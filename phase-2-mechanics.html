    MODULE 6

    Iterators & Generators

    💬 In plain English

    Anything you can loop over with for is an iterable (lists, strings, dicts, files…). A generator is a function that hands out values one at a time, only when asked, instead of building them all up front. You make one by using yield instead of return.

    📺
    Streaming vs downloading.

    A list is like downloading a whole movie before you watch it. A generator is like streaming: you get each piece just as you need it, so it barely uses any space.

    def countdown(n):
    while n > 0:
        yield n          # hand out n, then PAUSE here until asked again
        n -= 1

for number in countdown(3):
    print(number)        # → 3, then 2, then 1

    Step by step with next()

    gen = countdown(3)   # nothing runs yet — you just get a generator object
print(next(gen))     # → 3   runs until the first yield, then pauses
print(next(gen))     # → 2   resumes exactly where it paused
print(next(gen))     # → 1
next(gen)            # StopIteration — no more values (a for loop stops quietly here)
    🧠 Memory trick

    yield = pause button. next() = play.

    return ends a function for good; yield just pauses it, keeping every variable as it was.

    Why bother? Memory

    import sys

squares_list = [x * x for x in range(1_000_000)]   # builds all 1M numbers now
squares_gen  = (x * x for x in range(1_000_000))   # builds them on demand

print(sys.getsizeof(squares_list))   # → ~8,400,000 bytes (≈ 8 MB)
print(sys.getsizeof(squares_gen))    # → ~200 bytes

print(sum(squares_gen))              # works just like the list would

    Note the brackets: [ ... ] builds a list, ( ... ) makes a generator.

    ⚠️ Common mistake: using a generator twice
    evens = (n for n in range(10) if n % 2 == 0)
print(list(evens))   # → [0, 2, 4, 6, 8]
print(list(evens))   # → []   already used up!

    A generator is one-way, like a stream. Need the values again? Use a list, or create the generator again.

    🤔 Predict the output
    def greet():
    print("start")
    yield "hi"
    print("end")

g = greet()
print("created")
print(next(g))
    Show answer 
    created
start
hi

    Calling greet() runs nothing. The body only starts at the first next(), and pauses at yield — so "end" is never printed here.

    ✅ Remember
    • A function with yield becomes a generator: it produces values lazily, one at a time.
    • Generators use almost no memory — great for big files or long sequences.
    • They can only be looped over once.
    🔬 Go deeper — the iterator protocol, pipelines, yield from

    What a for loop really does

    it = iter([10, 20])        # calls __iter__()
while True:
    try:
        x = next(it)       # calls __next__()
    except StopIteration:
        break
    print(x)

    An iterable has __iter__ (a book). An iterator also has __next__ and remembers its position (a bookmark). Every iterator is iterable, not the other way round.

    Generator pipelines

    def read_lines(path):
    with open(path, encoding="utf-8") as f:
        yield from f                         # delegate to the file's own iterator

errors = (l for l in read_lines("app.log") if "ERROR" in l)
for line in errors:                          # one line at a time, even for a 50 GB file
    print(line)

    Infinite generators

    from itertools import islice

def fibonacci():
    a, b = 0, 1
    while True:
        yield a
        a, b = b, a + b

list(islice(fibonacci(), 8))    # → [0, 1, 1, 2, 3, 5, 8, 13]

    More details

    • yield from sub passes values (and send/throw/close) through to a sub-generator.
    • return value inside a generator ends it; the value is stored on the StopIteration.
    • gen.send(x) pushes a value back in — rare in modern code.

    Decorators

    💬 In plain English

    A decorator adds extra behaviour to a function without changing the function's code — logging, timing, checking permissions, retrying. The @name line above a function is the decorator.

    🎁
    Gift wrapping.

    The present (your function) stays the same. The wrapping adds something around it — and whoever receives it unwraps the wrapping first, then gets the present.

    🧠 The one rule behind every decorator

    @deco on top of def f just means f = deco(f).

    Python hands your function to deco and keeps whatever comes back in place of the original. Everything below follows from this one line.

    Why do I need a function inside a function?

    Because a decorator deals with two different moments:

    MomentWhen it happensHow often
    ⏱️ Decorating timeWhen Python reads the def with @ on itOnce
    📞 Call timeEvery time someone calls the functionEvery call

    Each moment needs its own function. Watch what happens with only one layer:

    def announce(func):
    print(f"Calling {func.__name__}...")   # ← runs at DECORATING time
    return func

@announce            # → Calling greet...   printed right here, ONCE
def greet():
    return "hello"

greet()              # → 'hello'    no message!
greet()              # → 'hello'    no message!

    The message printed once, when the def was read, and never again. To run code on every call, you need an inner function — the wrapper — that Python will call instead of the original:

    def announce(func):              # layer 1: runs ONCE, receives the function
    def wrapper():               # layer 2: runs on EVERY call
        print(f"Calling {func.__name__}...")
        return func()            # then run the original
    return wrapper               # greet now points to wrapper

@announce
def greet():
    return "hello"

greet()     # → Calling greet...   'hello'
greet()     # → Calling greet...   'hello'   ✅ every time
    🧠 Memory trick

    Outer function = set up once. Inner function = do every call.

    A real decorator: works with any function

    Two small upgrades make a wrapper work for any function: *args, **kwargs accepts whatever arguments the original takes, and return result passes its answer back.

    import functools
import time

def timer(func):
    @functools.wraps(func)                 # keep the original name and docstring (see below)
    def wrapper(*args, **kwargs):          # accept any arguments…
        start = time.perf_counter()
        result = func(*args, **kwargs)     # …and pass them straight through
        print(f"{func.__name__} took {time.perf_counter() - start:.2f}s")
        return result                      # hand the original's answer back
    return wrapper

@timer
def make_tea(minutes):
    time.sleep(minutes)
    return "tea ready"

print(make_tea(1))     # → make_tea took 1.00s
                       # → tea ready

    Why 3 layers when the decorator takes a setting?

    Look closely at the two ways a decorator line can look:

    @timer

    No parentheses. Python calls timer(func) straight away — timer receives the function.

    @repeat(3)

    Parentheses! Python runs repeat(3) first, before it has even looked at your function — repeat receives only the number 3.

    So repeat(3) can't do the decorating itself — it doesn't have the function yet. Its job is to remember the 3 and return a normal decorator. That's the extra layer. Here's @repeat(3) written out by hand:

    def repeat(times):                         # layer 1 — receives the SETTING
    def decorator(func):                   # layer 2 — receives the FUNCTION
        @functools.wraps(func)
        def wrapper(*args, **kwargs):      # layer 3 — receives the CALL's arguments
            for _ in range(times):
                result = func(*args, **kwargs)
            return result
        return wrapper
    return decorator

def wave():
    print("👋")

decorator = repeat(3)       # 1. runs layer 1 → remembers times=3, returns `decorator`
wave = decorator(wave)      # 2. runs layer 2 → remembers func,    returns `wrapper`
wave()                      # 3. runs layer 3 → 👋 👋 👋

# The @ line does steps 1 and 2 for you:
@repeat(3)
def wave():
    print("👋")

    So how do I decide: 2 layers or 3?

    Your decorator lineLayersWhat each layer receives
    @timer — no parentheses2the function → the call's arguments
    @repeat(3) — has parentheses3the setting → the function → the call's arguments
    🧠 Memory trick

    “Parentheses after the @? Add one more layer.”

    Each layer receives exactly one kind of thing, always in this order: settings → function → arguments.

    What is functools? Is wraps built in?

    functools is a module in Python's standard library — it comes with every Python install, so there's nothing to pip install, but you do need to import it. It's a toolbox of helpers for working with functions.

    functools.wraps is itself a decorator, and it fixes a side effect of wrapping. After decorating, the name add points to wrapper, so without help the function forgets who it was:

    def plain(func):
    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)
    return wrapper

@plain
def add(a, b):
    """Add two numbers."""
    return a + b

print(add.__name__, add.__doc__)    # → wrapper None   😕 name and docstring lost
    import functools

def keep_name(func):
    @functools.wraps(func)          # copy func's name and docstring onto wrapper
    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)
    return wrapper

@keep_name
def add(a, b):
    """Add two numbers."""
    return a + b

print(add.__name__, add.__doc__)    # → add Add two numbers.   ✅

    Notice that @functools.wraps(func) has parentheses — it's a 3-layer decorator, exactly like @repeat(3). Its setting is the original function, whose name and docstring it copies onto the wrapper.

    @classmethod, @staticmethodBuilt in — no importMethods that get the class, or nothing, instead of self

    ⚠️ Common mistakes
    • Forgetting return result in the wrapper — the decorated function then always returns None.
    • Forgetting @functools.wraps(func) — the function's name becomes "wrapper" and its docstring disappears.
    • Leaving off the parentheses — writing @repeat instead of @repeat(3) hands your function to the settings layer, and calling it fails with TypeError: … missing 1 required positional argument: 'func'.
    🤔 Predict the output
    def double_it(func):
    def wrapper(x):
        return func(x) * 2
    return wrapper

@double_it
def add_one(x):
    return x + 1

print(add_one(4))
    Show answer

    add_one(4) is really wrapper(4): the original gives 5, and the wrapper doubles it.

    ✅ Remember
    • A decorator wraps a function to add behaviour; @deco = f = deco(f).
    • Outer function runs once (gets the function); the inner wrapper runs on every call.
    • Parentheses after the @ (like @repeat(3)) → add a third, outermost layer for the setting.
    • functools ships with Python; @functools.wraps(func) keeps the original name and docstring.
    🔬 Go deeper — stacking order, class decorators

    Stacking decorators

    @A
@B
def f(): ...

# same as: f = A(B(f))
# B wraps first (closest to def); when called, A's wrapper runs first.

    Memory trick: built from the bottom, run from the top — like clothes: the bottom decorator is the innermost layer, the top one is the coat.

    Decorator code runs at definition time

    The decorator function runs once when Python reads the def (usually at import). The wrapper runs on every call.

    Class decorators

    def singleton(cls):
    instances = {}
    @functools.wraps(cls, updated=())
    def get_instance(*args, **kwargs):
        if cls not in instances:
            instances[cls] = cls(*args, **kwargs)
        return instances[cls]
    return get_instance

@singleton
class Database: pass

Database() is Database()    # → True

    Classes & Objects

    💬 In plain English

    A class is a blueprint; an object (instance) is a thing built from it. The class bundles data (attributes) with the actions that use it (methods).

    🏠
    Blueprint and houses.

    One blueprint (class House) can build many houses. Each house has its own paint colour (attributes), but they all share the same design (methods).

    class BankAccount:
    def __init__(self, owner, balance=0):    # runs when you create an account
        self.owner = owner                   # self = "this particular account"
        self.balance = balance

    def deposit(self, amount):               # a method: an action on the data
        self.balance += amount
        return self.balance

asha = BankAccount("Asha")
ravi = BankAccount("Ravi", 500)
asha.deposit(100)
print(asha.balance, ravi.balance)            # → 100 500   each object has its own data
    🧠 Memory trick

    self = “me, this one object”.

    asha.deposit(100) is really BankAccount.deposit(asha, 100) — Python passes the object in as self for you.

    Inheritance: reuse and extend

    class SavingsAccount(BankAccount):           # gets everything BankAccount has
    def __init__(self, owner, rate):
        super().__init__(owner)              # let the parent set up owner/balance
        self.rate = rate

    def add_interest(self):
        return self.deposit(self.balance * self.rate)

s = SavingsAccount("Neha", 0.05)
s.deposit(1000)                              # inherited method
print(s.add_interest())                      # → 1050.0

    Special (“dunder”) methods

    Methods with double underscores, like __init__, let your objects work with Python's built-in syntax — print(), len(), == and more.

    class Book:
    def __init__(self, title, pages):
        self.title = title
        self.pages = pages

    def __repr__(self):                       # how it looks when printed/debugged
        return f"Book({self.title!r}, {self.pages})"

    def __len__(self):                        # makes len(book) work
        return self.pages

    def __eq__(self, other):                  # makes == compare contents
        return (self.title, self.pages) == (other.title, other.pages)

b = Book("Dune", 412)
print(b)                       # → Book('Dune', 412)
print(len(b))                  # → 412
print(b == Book("Dune", 412))  # → True
    You writePython calls
    Book(...)__init__
    print(b)__str__ if defined, otherwise __repr__
    repr(b), showing it in a list__repr__
    len(b)__len__
    a == b__eq__
    a + b__add__
    🧠 Memory trick

    Dunder methods are your object's answers to Python's questions.

    “How long are you?” → __len__. “Are you equal to that?” → __eq__. “What do you look like?” → __repr__.

    The shortcut: @dataclass

    For classes that mainly hold data, @dataclass writes __init__, __repr__ and __eq__ for you:

    from dataclasses import dataclass

@dataclass
class Book:
    title: str
    pages: int

b = Book("Dune", 412)
print(b)                        # → Book(title='Dune', pages=412)
print(b == Book("Dune", 412))   # → True
    ⚠️ Common mistake: comparing objects without __eq__

    By default, == on your own objects checks whether they're the same object, not whether they hold the same data — so two identical-looking books are “not equal”. Define __eq__ or use @dataclass.

    🤔 Predict the output
    class Point:
    def __init__(self, x, y):
        self.x, self.y = x, y

print(Point(1, 2) == Point(1, 2))
print(Point(1, 2))

    False

    No __eq__ → == compares identity. No __repr__ → Python prints a generic label with a memory address. A @dataclass fixes both.

    ✅ Remember
    • Class = blueprint, object = thing built from it, self = the current object.
    • Use super().__init__(...) to let the parent class set itself up.
    • Dunder methods plug your objects into print, len, ==…; @dataclass writes the common ones for you.
    🔬 Go deeper — MRO, hashing rules, __slots__, __new__

    __repr__ vs __str__

    __repr__ is for developers (unambiguous, ideally looks like code); __str__ is for end users. Always write __repr__ — it's the fallback for str(), and containers like print([b]) always use it.

    Multiple inheritance and the MRO

    class D(B, C) — super() inside B calls C, not A.
    class A:
    def hi(self): print("A")
class B(A):
    def hi(self): print("B"); super().hi()
class C(A):
    def hi(self): print("C"); super().hi()
class D(B, C):
    def hi(self): print("D"); super().hi()

D().hi()        # → D B C A
D.__mro__       # → (D, B, C, A, object)

    super() means “the next class in the MRO”, not “my parent”. The order follows two rules: children before parents, left before right.

    The __eq__ / __hash__ contract

    If a == b, then hash(a) == hash(b) must also be true — otherwise sets and dicts break. Defining __eq__ alone makes Python set __hash__ = None, so instances can't go in a set. Hash the same fields you compare:

    class Point:
    def __init__(self, x, y): self.x, self.y = x, y
    def __eq__(self, other):
        if not isinstance(other, Point):
            return NotImplemented          # "I don't know — ask the other object"
        return (self.x, self.y) == (other.x, other.y)
    def __hash__(self):
        return hash((self.x, self.y))

    Return NotImplemented (not False) for unknown types so Python can try the other side's __eq__. And never change a field used in the hash after putting the object in a set — it becomes unfindable. @dataclass(frozen=True) gives you correct, immutable, hashable objects.

    @dataclass option__eq____hash__Mutable?
    default✅❌✅
    frozen=True✅✅❌

    Truthiness

    if obj: calls __bool__; if missing, it uses __len__() != 0; if that's missing too, the object is truthy.

    __slots__ and __new__

    • __slots__ = ("x", "y") drops the per-object __dict__: much less memory for millions of objects, but no adding new attributes later.
    • __new__ creates the object; __init__ fills it in. You rarely override __new__ (singletons, subclassing int/str).
    • @property, @classmethod and @staticmethod are built on descriptors — objects that control attribute access.

    Handling Errors & with

    💬 In plain English

    When something goes wrong, Python raises an exception (an error). If nobody handles it, the program crashes. try / except lets you catch it and respond. with makes sure cleanup (like closing a file) always happens.

    text = "abc"

try:
    number = int(text)                 # this line might fail
except ValueError:
    print("That's not a number!")      # → That's not a number!

    The four blocks

    try:
    file = open("data.txt", encoding="utf-8")
except FileNotFoundError:
    print("No file — using defaults")  # runs only if that error happened
else:
    print(file.read())                 # runs only if NO error happened
    file.close()
finally:
    print("done")                      # ALWAYS runs, error or not
    🧠 Memory trick

    Try it → except if it fails → else if it worked → finally no matter what.

    Catch specific errors

    try:
    price = prices[item]
except KeyError:                  # ✅ only the error you expect
    price = 0

# ❌ Avoid a bare except: it hides real bugs and even swallows Ctrl+C
try:
    price = prices[item]
except:
    price = 0

    If you really need a catch-all, write except Exception as e: and log e.

    Raising your own errors

    def withdraw(balance, amount):
    if amount > balance:
        raise ValueError("Not enough money")
    return balance - amount

try:
    withdraw(100, 500)
except ValueError as e:
    print(e)                      # → Not enough money

    with: automatic cleanup

    🚪
    A self-closing door.

    However you leave the room — calmly or running from an error — the door closes behind you.

    with open("notes.txt", encoding="utf-8") as f:
    content = f.read()
# the file is closed here automatically — even if read() raised an error

    You can make your own with @contextmanager: code before yield is the setup, code after is the cleanup.

    from contextlib import contextmanager
import time

@contextmanager
def timer(label):
    start = time.perf_counter()        # setup
    try:
        yield                          # the body of the with-block runs here
    finally:
        print(f"{label}: {time.perf_counter() - start:.2f}s")   # cleanup

with timer("nap"):
    time.sleep(0.5)                    # → nap: 0.50s
    🤔 Predict the output
    def check():
    try:
        return "from try"
    finally:
        print("cleanup")

print(check())
    Show answer 
    cleanup
from try

    finally runs even when try returns — right before the function actually exits.

    ✅ Remember
    • Wrap only the risky line in try, and catch the specific error.
    • else = success path, finally = always.
    • Use with for files, locks and connections so cleanup is guaranteed.
    🔬 Go deeper — the exception hierarchy, chaining, __exit__

    The hierarchy that matters

    • BaseException ← never catch this
      • SystemExit — sys.exit()
      • KeyboardInterrupt — Ctrl+C
      • Exception ← catch this (or narrower)
        • ValueError, TypeError, KeyError, OSError, …

    A bare except: catches BaseException — including Ctrl+C and sys.exit() — so the program can't be stopped normally.

    Custom exceptions and chaining

    import json

class APIError(Exception):
    def __init__(self, status, message):
        self.status = status
        super().__init__(f"HTTP {status}: {message}")

try:
    json.loads("{bad json")
except json.JSONDecodeError as e:
    raise APIError(400, "Invalid JSON") from e    # keeps the original cause in the traceback

    Class-based context managers

    class Timer:
    def __enter__(self):
        self.start = time.perf_counter()
        return self                      # bound to `as t`
    def __exit__(self, exc_type, exc, tb):
        print(time.perf_counter() - self.start)
        return False                     # True would SWALLOW the exception

    Comprehensions & Handy Tools

    💬 In plain English

    A comprehension is a one-line way to build a new list (or dict, or set) from an existing one — transforming items, filtering them, or both.

    Regular loop

    squares = []
for n in range(5):
    squares.append(n * n)

    Comprehension

    squares = [n * n for n in range(5)]
# → [0, 1, 4, 9, 16]
    🧠 Memory trick — read it like English

    [ what_you_want for item in items if condition ]

    “Give me what I want, for each item in items, if condition.”

    prices = [120, 45, 300, 80]

[p for p in prices if p < 100]              # filter    → [45, 80]
[p * 1.18 for p in prices]                  # transform → add 18% tax to each
["cheap" if p < 100 else "pricey" for p in prices]
                                            # → ['pricey', 'cheap', 'pricey', 'cheap']

    Filtering if goes at the end. An if/else that picks a value goes at the front.

    Same idea, other containers

    names = ["asha", "ravi", "neha"]

{n: len(n) for n in names}       # dict → {'asha': 4, 'ravi': 4, 'neha': 4}
{len(n) for n in names}          # set  → {4}
(n.title() for n in names)       # generator — lazy (see Module 6)

    Loop helpers you'll use every day

    students = ["Asha", "Ravi"]
marks = [91, 78]

for i, name in enumerate(students, start=1):   # index + value
    print(i, name)                             # → 1 Asha, then 2 Ravi

for name, mark in zip(students, marks):        # walk two lists together
    print(name, mark)                          # → Asha 91, then Ravi 78

any(m < 35 for m in marks)    # → False   is ANY item true?
all(m >= 35 for m in marks)   # → True    are ALL items true?

    Remember answers with @lru_cache

    from functools import lru_cache

@lru_cache
def fib(n):
    return n if n < 2 else fib(n - 1) + fib(n - 2)

fib(100)     # → 354224848179261915075   instant — each answer is computed once
    ⚠️ Common mistake: comprehensions that are too clever

    If a comprehension needs two loops and conditions, or you have to read it twice, write a normal for loop. Readable beats short.

    🤔 Predict the output
    print([x * 2 for x in range(5) if x % 2 == 0])
    Show answer 
    [0, 4, 8]

    Keep the even numbers (0, 2, 4), then double each one.

    ✅ Remember
    • [expr for item in items if cond] — brackets decide the type: [] list, {} set/dict, () generator.
    • enumerate for index + value, zip for parallel lists, any/all for checks.
    • @lru_cache remembers results of expensive calls.
    🔬 Go deeper — nested comprehensions, functools, itertools

    Nested comprehensions

    matrix = [[1, 2], [3, 4]]
[n for row in matrix for n in row]     # → [1, 2, 3, 4]
# the for-clauses read in the same order as nested loops

    itertools top picks

    from itertools import chain, islice, groupby, product, combinations

list(chain([1, 2], [3]))            # → [1, 2, 3]
list(islice(range(100), 3))         # → [0, 1, 2]
list(combinations("ABC", 2))        # → AB AC BC

[(k, len(list(g))) for k, g in groupby(nums)]   # → [(1, 2), (2, 1), (1, 1)]

    groupby only groups neighbouring equal items — sort first if you want one group per key.

    ⚠️ Common mistakes

    The traps that catch almost everyone at least once.

    1. Looping over a generator a second time and getting nothing.
    2. Forgetting return result in a decorator's wrapper.
    3. Forgetting @functools.wraps — the function's name becomes wrapper.
    4. Forgetting self as the first method parameter.
    5. Expecting == to compare your objects' data without defining __eq__ (or using @dataclass).
    6. Forgetting super().__init__() in a subclass, so parent attributes are never set.
    7. Using a bare except: — catch the specific error.
    8. Putting too much code inside try — wrap only the risky line.
    9. Opening files without with and forgetting to close them.
    10. Writing comprehensions so clever nobody can read them.
