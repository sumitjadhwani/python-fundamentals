    MODULE 11

    Compilation & Bytecode

    🔑 Core idea

    Python is compiled to bytecode, then that bytecode is interpreted by the Python Virtual Machine (PVM). So it's both — there is a compile step, but it produces bytecode (.pyc), not machine code.

    Source .py → Tokenizer → AST → Compiler → Bytecode .pyc → PVM executes
    🧠 Memory trick

    “Translate once, cook many times.”

    The compiler translates your recipe into kitchen shorthand (bytecode) and keeps it in __pycache__. The chef (PVM) cooks from the shorthand every run.

    Peek at the bytecode with dis

    import dis

def add(a, b):
    return a + b

dis.dis(add)
      RESUME                            0
  LOAD_FAST_BORROW_LOAD_FAST_BORROW 1 (a, b)    ← push a and b
  BINARY_OP                         0 (+)       ← pop two, push a + b
  RETURN_VALUE                                  ← pop and return

    Output from Python 3.14. Opcode names change between versions (older ones show LOAD_FAST / BINARY_ADD) — the shape is what matters.

    It's a stack machine

    🧠 Memory trick — a stack of plates

    LOAD_* puts a plate on the stack. BINARY_OP takes two plates off and puts the result back. STORE_* takes the top plate and gives it a name. RETURN_VALUE hands the top plate to the caller.

    .pyc files

    • Live in __pycache__/, named per version: module.cpython-314.pyc.
    • Rebuilt when the source changes (timestamp or hash check).
    • Version-specific — 3.12 bytecode won't run on 3.14.
    • PYTHONDONTWRITEBYTECODE=1 stops Python writing them.
    • The script you run directly isn't cached — only imported modules are.

    Constant folding

    def seconds_per_day():
    return 24 * 60 * 60

seconds_per_day.__code__.co_consts   # (24, 86400) — 86400 was computed at COMPILE time

# Folding has limits: "a" * 1000 is folded, a huge "a" * 10_000 is not
# (CPython won't bake very large constants into the .pyc)

    Code objects

    def example(x):
    return x * 2 + 1

code = example.__code__
code.co_varnames     # ('x',)         local names
code.co_consts       # constants used (exact tuple varies by version)
code.co_stacksize    # max stack depth the function needs

c = compile("1 + 2", "<string>", "eval")   # compile a string yourself
eval(c)              # 3
    ⚠️ Don't forget
    • “Interpreted vs compiled?” → both: compiled to bytecode, then interpreted.
    • Bytecode isn't portable across Python versions.
    • Since 3.11 the interpreter specializes hot bytecode (adaptive interpreter) — one reason modern Python got faster.
    🤔 Predict the output
    def f():
    return 60 * 60

print(3600 in f.__code__.co_consts)
    Show answer 
    True

    The compiler folded 60 * 60 into 3600, so the multiplication never happens at runtime.

    MODULE 12

    Memory Management

    🔑 Core idea

    CPython frees memory mainly with reference counting — deterministic and immediate. A separate cyclic garbage collector cleans up reference cycles that refcounting alone can never free.

    🧠 Memory trick — bouncer & security sweep

    Refcounting is the bouncer at the door: the instant the last reference leaves, the object is out. The GC is a periodic security sweep that finds groups of objects only holding on to each other and evicts them together.

    Reference counting

    import sys

x = [1, 2, 3]
sys.getrefcount(x)   # 2 → x, plus the temporary reference for the call itself

y = x                # 3
del y                # 2
del x                # 0 → freed immediately (deterministic!)

    Reference cycles

    import gc

a = []
b = []
a.append(b)          # a → b
b.append(a)          # b → a   ← cycle: refcounts never reach 0
del a, b             # unreachable, but not freed yet...

gc.collect()         # 2 → the cycle collector found and freed both lists

    Generations

    Most objects die young, so the GC checks new objects often and old ones rarely.

    Python versionLayoutgc.get_threshold()
    ≤ 3.13 (classic)3 generations: gen 0 (new) → gen 1 → gen 2 (long-lived)(700, 10, 10)
    3.14+Incremental GC: a young and an old generation, scanned in small steps to shorten pauses(2000, 10, 0)

    Classic rule: gen 0 runs when allocations − deallocations exceed 700; gen 1 every 10 gen-0 runs; gen 2 every 10 gen-1 runs. Interview answers usually quote this model.

    Memory allocator layers

    ┌───────────────────────────────────────────────┐
│ Layer 3: object-specific caches (ints, lists…)│
├───────────────────────────────────────────────┤
│ Layer 2: pymalloc — objects ≤ 512 bytes        │
│   Arena (256 KB) → Pool (4 KB) → Block (8–512 B)│
├───────────────────────────────────────────────┤
│ Layer 1: the OS malloc — anything bigger        │
└───────────────────────────────────────────────┘

    Weak references

    import weakref

class Thing: pass

obj = Thing()
ref = weakref.ref(obj)    # does NOT bump the refcount
ref()                     # <Thing object at ...>
del obj
ref()                     # None — the object is gone

cache = weakref.WeakValueDictionary()   # entries vanish when values die

    Finding leaks with tracemalloc

    import tracemalloc

tracemalloc.start()
run_suspicious_code()
snapshot = tracemalloc.take_snapshot()
for stat in snapshot.statistics("lineno")[:5]:
    print(stat)           # top 5 lines by memory allocated
    ⚠️ Don't forget
    • __del__ is unreliable — timing is unpredictable and it can resurrect objects. Use context managers for cleanup.
    • gc.disable() stops only the cycle collector. Refcounting keeps working.
    • Common real leaks: unbounded global caches, closures capturing big objects, C extensions.
    🧠 Memory trick

    “gc.disable() sends the sweepers home — the bouncer stays.”

    🤔 Predict the output
    import gc, weakref

class Node: pass

n = Node()
r = weakref.ref(n)
gc.disable()
del n
print(r())
    Show answer 
    None

    No cycle here, so refcounting frees the object the moment n is deleted — disabling the GC doesn't matter.

    MODULE 13

    The GIL (Global Interpreter Lock)

    🔑 Core idea

    The GIL is a mutex that lets only one thread run Python bytecode at a time. It exists because CPython's reference counts aren't thread-safe. It blocks CPU parallelism with threads — but I/O-bound threads work fine, because the GIL is released while waiting on I/O.

    🧠 Memory trick — the one-microphone room

    Only the person holding the mic (thread) can speak (run bytecode). When someone steps out for food (I/O), the mic is free for others. Shouting louder (more threads) doesn't make two people speak at once.

    Thread 1:  ████░░░░████░░░░████
Thread 2:  ░░░░████░░░░████░░░░
               ↑ the interpreter asks for a switch every 5 ms (sys.getswitchinterval())

    What the GIL does — and doesn't — protect

    ✅ Protects

    • CPython internals (refcounts, allocator)
    • Each single bytecode instruction

    ❌ Does NOT protect

    • Your data structures
    • Multi-step operations like counter += 1
    • The logic of your program
    🧠 Memory trick

    “The GIL guards Python's guts, not your data.”

    Why counter += 1 isn't thread-safe

    LOAD_GLOBAL     counter   ← read
LOAD_SMALL_INT  1
BINARY_OP       (+=)      ← add
STORE_GLOBAL    counter   ← write      (a thread switch can land between any two)
    import threading

counter = 0
lock = threading.Lock()

def increment():
    global counter
    for _ in range(1_000_000):
        with lock:            # without the lock, updates can be lost
            counter += 1

threads = [threading.Thread(target=increment) for _ in range(2)]
for t in threads: t.start()
for t in threads: t.join()
print(counter)                # 2000000 — guaranteed only because of the lock

    When is the GIL released?

    • Blocking I/O — files, sockets, time.sleep()
    • Many C extensions while crunching numbers (NumPy, hashing, compression, DB drivers)

    The decision rule

    BottleneckUseWhy
    I/O-boundThreads (or asyncio)GIL is released while waiting
    CPU-boundMultiprocessingEach process has its own GIL
    Bothasyncio + ProcessPoolExecutorAsync for I/O, processes for compute

    The free-threaded future (PEP 703)

    Python 3.13 shipped an experimental free-threaded build with no GIL (python3.13t). In 3.14 that build is officially supported, but it's still a separate build — the regular python keeps the GIL. Check with sys._is_gil_enabled().

    ⚠️ Don't forget
    • The GIL makes CPython safe, not your code — always lock shared mutable state.
    • Threads don't speed up pure-Python CPU work; they can even slow it down.
    🤔 Predict the output
    # Same counter program as above, but WITHOUT the lock.
# What does print(counter) show?
    Show answer 
    Unpredictable — anything up to 2000000.

    On some versions and machines it often prints the right number, which makes the bug worse: the code is still wrong and can lose updates at any time. Correctness must come from the lock, not from luck.

    ⚠️ Gotchas checklist

    Skim this the night before an interview.

    1. Python is compiled (to bytecode), not purely interpreted.
    2. .pyc is version-specific.
    3. Constant folding: 24 * 60 * 60 is computed at compile time.
    4. __del__ timing is unpredictable — use context managers.
    5. Refcounting is deterministic: refcount 0 → freed immediately.
    6. The cyclic GC only handles cycles — refcounting does most of the work.
    7. gc.disable() disables the cycle collector only.
    8. The GIL protects CPython internals, not your data structures.
    9. counter += 1 is not atomic — use a lock.
    10. I/O-bound → threads work. CPU-bound → multiprocessing.
    11. Free-threaded (no-GIL) Python is a separate build, not the default.
    12. pymalloc handles objects ≤ 512 bytes; bigger ones go to the OS allocator.
