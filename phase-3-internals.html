    MODULE 11

    From Source Code to Running Code

    💬 In plain English

    Your computer can't run Python text directly. So when you run a .py file, Python first translates your code into a list of tiny, simple instructions called bytecode. Then a program inside Python, the Python Virtual Machine (PVM), carries out those instructions one by one.

    🧑‍🍳
    A recipe turned into kitchen steps.

    Your code is a recipe written in full sentences. Python rewrites it as short numbered steps (“take a”, “take b”, “add them”, “serve”) — that's bytecode. The chef (the PVM) follows the steps. The rewritten steps are even saved, so next time the chef can skip the rewriting.

    The four stages, in plain words

    Source .py→ Tokenizer→ Parser (AST)→ Compiler→ Bytecode→ PVM runs it
    StageWhat it doesFor x = 1 + 2
    TokenizerChops the text into “words” and symbolsx · = · 1 · + · 2
    ParserArranges the words into a tree that shows the structure — the AST (abstract syntax tree)“assign to x the result of adding 1 and 2”
    CompilerTurns the tree into bytecode instructions“load 3” (already folded!), “store it in x”
    PVMExecutes the instructions one by oneputs 3 in x

    Syntax errors are caught in the first two stages — that's why a typo at the bottom of a file stops the whole file from running, even the lines above it.

    🧠 Memory trick

    “Translate once, run many times.”

    Python is both compiled (to bytecode) and interpreted (the PVM runs the bytecode).

    What does bytecode look like?

    The built-in dis module (“disassemble”) shows the bytecode for any function:

    import dis

def add(a, b):
    return a + b

dis.dis(add)
      RESUME                            0
  LOAD_FAST_BORROW_LOAD_FAST_BORROW 1 (a, b)   ← fetch a and b
  BINARY_OP                         0 (+)      ← add them
  RETURN_VALUE                                 ← hand back the result

    Output from Python 3.14. Instruction names change between versions (older ones show LOAD_FAST and BINARY_ADD) — the idea stays the same. RESUME is just bookkeeping at the start of every function.

    How the PVM runs it: a stack of plates

    The PVM keeps a pile of values called the stack. Instructions put values on top, take them off, and put results back. Here is add(2, 3) step by step:

    InstructionWhat happensStack afterwards
    LOAD … a, bPut a and then b on the pile[2, 3]
    BINARY_OP +Take the top two off, add them, put the answer back[5]
    RETURN_VALUETake the top value off and return it[] → returns 5
    🧠 Memory trick — a stack of plates

    LOAD = put a plate on top. BINARY_OP = take two plates, put one back. STORE = take the top plate and write a name on it. RETURN_VALUE = hand the top plate to the caller.

    .pyc files: saved bytecode

    Translating takes time, so when you import a module Python saves its bytecode in a __pycache__ folder, in a file like helpers.cpython-314.pyc. Next time, if the .py file hasn't changed, Python loads the saved bytecode and skips the translation — your program starts faster.

    • The file name includes the Python version (cpython-314), because bytecode from one version doesn't work on another.
    • If you edit the .py file, Python notices and rebuilds the .pyc.
    • The script you run directly (python main.py) isn't saved — only modules it imports.
    • Safe to delete: __pycache__ folders are rebuilt automatically, and they're usually listed in .gitignore.

    Constant folding: doing the maths ahead of time

    💬 In plain English

    If part of your code only uses fixed values — numbers or strings typed directly into the code — the compiler works out the answer once, while translating, and stores just the answer. It's called folding because several values are folded into one.

    import dis

def seconds_per_day():
    return 24 * 60 * 60

dis.dis(seconds_per_day)
#   LOAD_CONST   86400      ← the multiplication is already done!
#   RETURN_VALUE

    Why you care: you can write the readable 24 * 60 * 60 instead of a mystery number like 86400, and it costs nothing — the multiplying never happens while your program runs.

    When it can't fold

    Folding only works when every value is known before the program runs. Anything involving a variable or a function call has to wait until runtime:

    def hours_to_seconds(hours):
    return hours * 60 * 60      # NOT folded: read as (hours * 60) * 60,
                                # and hours isn't known until the call

def hours_to_seconds(hours):
    return hours * (60 * 60)    # 60 * 60 IS folded → hours * 3600

len("hello")                    # NOT folded: function calls always run at runtime

    Python also refuses to fold results that would be huge (like "a" * 10_000), so the saved bytecode stays small.

    🧠 Memory trick

    “Only literals fold.”

    Numbers and strings typed straight into the code can be pre-computed. Variables and function calls can't.

    Code objects: where the bytecode lives

    💬 In plain English

    When Python compiles a function, it packs everything needed to run it into a code object: the bytecode instructions, the constants it uses, and the names of its variables. Every function keeps its code object in func.__code__.

    🗂️
    The steps vs the recipe card.

    The code object is the list of numbered steps plus the ingredient list. The function object is the recipe card that holds those steps and adds its own label: its name, its default values, and which file's global variables it can see. Two functions can share the same steps but have different labels.

    def greet(name, excited=False):
    message = "Hello, " + name
    if excited:
        message = message.upper()
    return message

code = greet.__code__
print(code.co_argcount)    # → 2                              how many parameters
print(code.co_varnames)    # → ('name', 'excited', 'message')  local variable names
print(code.co_consts)      # → ('Hello, ',)                    fixed values it uses
print(code.co_names)       # → ('upper',)                      other names it looks up
print(len(code.co_code))   # → 72                              raw bytecode, in bytes

print(greet.__defaults__)  # → (False,)   defaults live on the FUNCTION, not the code
    AttributePlain meaning
    co_codeThe raw bytecode instructions
    co_constsFixed values used in the body (strings, numbers, folded results)
    co_varnamesParameter and local variable names
    co_namesGlobal names and attributes the code looks up (like .upper)
    co_argcountNumber of positional parameters
    co_stacksizeHow tall the “stack of plates” can get while it runs

    Exact numbers (like the byte count) differ between Python versions. Small numbers such as 60 may not appear in co_consts in 3.14 — they get their own LOAD_SMALL_INT instruction.

    Making code objects yourself

    code = compile("price * qty", "<calc>", "eval")   # text → code object
print(type(code).__name__)                         # → code
print(eval(code, {"price": 50, "qty": 3}))         # → 150   run it with these variables

    This is what Python does behind the scenes for every file and function. You'll rarely need it, but tools like debuggers, test frameworks and template engines use it.

    🤔 Predict the output
    def f():
    return 60 * 60

def g(x):
    return x * 60 * 60

print(3600 in f.__code__.co_consts)
print(3600 in g.__code__.co_consts)
    Show answer 
    True
False

    60 * 60 uses only literals, so it folds into 3600. In g, Python computes x * 60 first, which can't be known ahead of time, so nothing folds.

    ✅ Remember
    • Python translates source → bytecode, then the PVM runs the bytecode on a stack.
    • .pyc files in __pycache__ are saved bytecode so imports start faster.
    • Constant folding pre-computes expressions made only of literals.
    • A code object holds a function's bytecode, constants and variable names; the function object adds its name, defaults and globals.
    🔬 Go deeper — the AST, the adaptive interpreter, .pyc details

    See the AST yourself

    import ast
print(ast.dump(ast.parse("x = 1 + 2")))
# Module(body=[Assign(targets=[Name(id='x', ctx=Store())],
#                     value=BinOp(left=Constant(value=1), op=Add(), right=Constant(value=2)))])

    Linters, formatters and type checkers work on this tree instead of on raw text.

    The adaptive interpreter (3.11+)

    While your program runs, Python watches which instructions run a lot. A general BINARY_OP + that keeps seeing two integers is swapped for a faster “add two ints” version. This specialization is a big reason Python 3.11+ is noticeably faster than 3.10. You can peek with dis.dis(func, adaptive=True) after calling the function many times.

    .pyc details

    • By default Python checks the source file's modification time and size to decide whether the .pyc is stale; hash-based checking is also available.
    • PYTHONDONTWRITEBYTECODE=1 (or python -B) stops Python writing .pyc files.
    • python -m compileall . pre-compiles a whole project, which some deployments do to speed up the first start.

    exec vs eval

    compile(..., "eval") is for a single expression and is run with eval(), which returns its value. compile(..., "exec") is for statements and is run with exec(), which returns None. Never run text from untrusted users this way — it can do anything your program can.

    MODULE 12

    Memory Management: How Python Cleans Up

    💬 In plain English

    In Python you never free memory yourself. Python keeps a count of how many things are using each object. The moment nothing uses an object any more, Python throws it away. A backup cleaner, the garbage collector, handles one tricky case: objects that only point at each other.

    🎈
    Balloons on strings.

    Every object is a balloon. Every variable, list slot or dict entry that refers to it is a string someone is holding. While at least one string is held, the balloon stays. When the last string is let go, the balloon floats away — the memory is freed.

    1. Reference counting: the main cleaner

    The number of strings on a balloon is its reference count. To see the moment an object is freed, this demo uses __del__, a method Python calls just before throwing an object away:

    class Balloon:
    def __init__(self, name):
        self.name = name
    def __del__(self):                 # demo only: shows the moment it's freed
        print(f"{self.name} popped")

a = Balloon("red")     # 1 string  (a)
b = a                  # 2 strings (a, b)
del a                  # 1 string left — nothing happens
print("still here")    # → still here
del b                  # 0 strings → → red popped
    🧠 Memory trick

    “del lets go of a string — it doesn't pop the balloon.”

    The object is freed only when the last reference is gone.

    What counts as a string?

    Not just variables. Anything that holds on to an object keeps it alive:

    blue = Balloon("blue")
party = [blue]           # the list holds a string too
del blue
print("list still holds it")   # → list still holds it
party.clear()                  # → blue popped

def make():
    tmp = Balloon("green")     # a local variable is a string…
    print("inside")
make()                         # → inside
                               # → green popped   …let go when the function returns

    That's why most memory in Python cleans itself up without you thinking about it: local variables vanish when functions return, and temporary objects vanish as soon as you're done with them.

    2. The one problem: objects holding each other

    🪢
    Two balloons tied to each other.

    Nobody is holding either balloon — but each one is tied to the other, so each still has one string. Counting strings alone, they'd stay forever. This is called a reference cycle.

    import gc

x = Balloon("A")
y = Balloon("B")
x.friend = y           # A holds B
y.friend = x           # B holds A   ← a cycle
del x, y               # we let go — but nothing pops!
print("nothing popped yet")   # → nothing popped yet

gc.collect()           # → A popped
                       # → B popped   the garbage collector found the cycle

    3. The garbage collector: the backup cleaner

    The garbage collector (gc) wakes up every so often, looks for groups of objects that only point at each other and that nothing else can reach, and frees them. It runs automatically — you almost never call gc.collect() yourself.

    🧠 Memory trick — bouncer and cleaning crew

    Reference counting is the bouncer: the instant the last guest stops holding an object, it's out — immediately. The garbage collector is the cleaning crew that sweeps through now and then to clear the tangled leftovers the bouncer can't see.

    To keep the sweeps cheap, it uses a simple observation: most objects die young. So it checks new objects often and long-lived survivors rarely. These age groups are called generations.

    4. Weak references: looking without holding

    Sometimes you want to keep track of an object without keeping it alive — for example, a cache. A weak reference points at a balloon without holding its string.

    import weakref

big = Balloon("gold")
ref = weakref.ref(big)   # look, but don't hold
print(ref().name)        # → gold
del big                  # → gold popped   the weak ref didn't keep it alive
print(ref())             # → None
    ⚠️ Common mistake 1: using __del__ for cleanup

    __del__ is fine for a demo, but in real code you can't be sure when it runs (cycles delay it, and it may not run at all when the program exits). For files, connections and locks, use with (Phase 2, Module 9) — cleanup then happens at a known moment.

    ⚠️ Common mistake 2: “leaks” from things you forgot you're holding

    Python can't free an object while something still references it. The classic leak is a cache that only ever grows:

    _cache = {}

def load_user(user_id):
    if user_id not in _cache:
        _cache[user_id] = fetch_from_db(user_id)   # ❌ every user stays in memory forever
    return _cache[user_id]

from functools import lru_cache

@lru_cache(maxsize=1000)                           # ✅ keeps only the 1000 most recently used
def load_user(user_id):
    return fetch_from_db(user_id)
    🤔 Predict the output
    nums = [1, 2, 3]
backup = nums
del nums
print(backup)
    Show answer 
    [1, 2, 3]

    del nums only removed one name. backup is still holding the list, so it stays alive.

    ✅ Remember
    • Python counts references; when the count hits zero, the object is freed immediately.
    • Objects that only point at each other (cycles) are cleaned up later by the garbage collector.
    • del removes a name, not the object.
    • Use with for cleanup, and watch out for caches and lists that grow forever.
    🔬 Go deeper — getrefcount, generations, allocators, leak hunting

    Seeing the count

    import sys
x = [1, 2, 3]
sys.getrefcount(x)   # → 2   x, plus a temporary reference for the call itself

    The count always reads one higher than you'd expect, because passing x into getrefcount creates a reference.

    Generations in numbers

    Python versionLayoutgc.get_threshold()
    ≤ 3.13 (classic)3 generations: gen 0 (new) → gen 1 → gen 2 (long-lived)(700, 10, 10)
    3.14+Incremental: a young and an old generation, scanned in small steps so pauses are shorter(2000, 10, 0)

    Classic rule: gen 0 is checked when allocations minus deallocations exceed 700; gen 1 every 10 gen-0 runs; gen 2 every 10 gen-1 runs. Interview answers usually quote this model.

    gc.disable()

    Turns off only the cycle collector — reference counting keeps working. Some apps disable it during hot paths and call gc.collect() at quiet moments.

    How memory is actually handed out

    ┌───────────────────────────────────────────────┐
│ Layer 3: object-specific caches (ints, lists…)│
├───────────────────────────────────────────────┤
│ Layer 2: pymalloc — objects ≤ 512 bytes        │
│   Arena (256 KB) → Pool (4 KB) → Block (8–512 B)│
├───────────────────────────────────────────────┤
│ Layer 1: the OS malloc — anything bigger        │
└───────────────────────────────────────────────┘

    Freed small objects go back to Python's own pools for reuse, so a process's memory use may not shrink right away even after objects die.

    Finding leaks with tracemalloc

    import tracemalloc

tracemalloc.start()
run_suspicious_code()
snapshot = tracemalloc.take_snapshot()
for stat in snapshot.statistics("lineno")[:5]:
    print(stat)          # the 5 source lines that allocated the most memory

    More on weak references

    weakref.WeakValueDictionary is a dict whose entries disappear automatically when their values are freed — a cache that never keeps objects alive by itself.

    MODULE 13

    The GIL (Global Interpreter Lock)

    First, four words you need

    WordPlain meaning
    ThreadA separate line of work inside one program. A program with two threads can, in principle, do two things at once — like a cook stirring a pot while a helper chops vegetables.
    Lock (mutex)A “one at a time” token. Whoever holds it may continue; everyone else waits until it's handed back.
    CPU-boundWork that keeps the processor busy calculating: maths, resizing images, parsing big files.
    I/O-boundWork that mostly waits: for a web page, a database, a file on disk, a timer.
    💬 In plain English

    The GIL is one big lock inside CPython (the standard Python). The rule: only one thread can run Python code at any moment. If you start four threads, they take turns very quickly instead of running side by side. While a thread is waiting (for the network, a file, sleep), it gives the lock up so another thread can run.

    🎤
    A meeting with one microphone.

    Only the person holding the mic can speak. People pass it around quickly, so everyone gets turns — but never two at once. When someone steps out to take a phone call (waiting on I/O), they hand the mic over and others carry on.

    Why does the GIL exist?

    Remember reference counting from Module 12: every object has a count of how many things use it. If two threads changed the same count at exactly the same moment, one update could be lost — and Python might free an object that's still in use, crashing the program. Putting a lock on every object would make normal single-threaded code slower. One big lock is the simple, fast solution: no two threads ever touch Python's internals at the same time.

    What it means in practice

    import threading, time

def count_down(n):            # CPU-bound: pure calculation
    while n > 0:
        n -= 1

def run_twice_with_threads(func, arg):
    threads = [threading.Thread(target=func, args=(arg,)) for _ in range(2)]
    for t in threads: t.start()
    for t in threads: t.join()          # wait for both to finish

# CPU-bound: threads take turns, so there is NO speed-up
#   count_down twice, one after the other   → ~1.3 s
#   count_down twice, in two threads        → ~1.3 s

# I/O-bound: waiting threads hand over the GIL, so they DO overlap
#   time.sleep(1) twice, one after the other → 2.0 s
#   time.sleep(1) twice, in two threads      → 1.0 s
run_twice_with_threads(time.sleep, 1)

    Timings measured on one machine with Python 3.14; yours will differ, but the pattern holds.

    🧠 Memory trick

    “Waiting work shares the mic. Thinking work fights over it.”

    Threads help when your program mostly waits. They don't help when it mostly calculates.

    The GIL does NOT make your code thread-safe

    This surprises almost everyone. The GIL protects Python's internals, not your variables. Take counter += 1. It looks like one step, but it's really three: read the value, add one, write it back. Python can switch threads between any two of them:

    StepThread AThread Bcounter
    1reads 55
    2— switch —reads 55
    3adds 1, writes 66
    4adds 1, writes 66 ← should be 7!

    Two increments happened but only one counted. This is a race condition. The fix is your own lock around the read-add-write:

    import threading

counter = 0
lock = threading.Lock()

def increment():
    global counter
    for _ in range(1_000_000):
        with lock:            # only one thread at a time inside this block
            counter += 1

threads = [threading.Thread(target=increment) for _ in range(2)]
for t in threads: t.start()
for t in threads: t.join()
print(counter)                # → 2000000   guaranteed, because of the lock
    🧠 Memory trick

    “The GIL guards Python's guts, not your data.”

    So what should I use?

    Your program mostly…UseWhy
    Waits (web requests, files, databases)Threads or asyncioWaiting threads hand over the GIL
    Calculates (maths, images, parsing)Multiple processesEach process is a separate Python with its own GIL
    Bothasyncio + a process poolAsync for waiting, processes for calculating

    Phase 4 covers each of these in detail.

    Python without the GIL

    There is now a special free-threaded build of Python with no GIL, where threads really can calculate side by side. It arrived as an experiment in 3.13 and is officially supported in 3.14 — but it's a separate download (often named python3.14t), not the normal python. Check which one you have with sys._is_gil_enabled().

    🤔 Predict the output
    # The same counter program as above, but WITHOUT the lock.
# What does print(counter) show?
    Show answer 
    Unpredictable — anything up to 2000000.

    On some machines it often prints the right number, which makes the bug sneakier: the code is still wrong and can lose updates at any time. Correctness must come from the lock, not from luck.

    ✅ Remember
    • The GIL lets only one thread run Python code at a time; it exists to protect reference counts.
    • Threads speed up waiting (I/O), not calculating (CPU). For calculating, use processes.
    • The GIL doesn't protect your variables — use a Lock for shared data.
    🔬 Go deeper — switch interval, bytecode of +=, C extensions

    How often threads switch

    Thread 1:  ████░░░░████░░░░████
Thread 2:  ░░░░████░░░░████░░░░
               ↑ a waiting thread asks for the GIL; the holder hands it over
                 after about 5 ms (sys.getswitchinterval() → 0.005)

    The bytecode behind counter += 1

    LOAD_GLOBAL     counter   ← read
LOAD_SMALL_INT  1
BINARY_OP       (+=)      ← add
STORE_GLOBAL    counter   ← write     (a switch can land between any two)

    The GIL makes each single instruction safe, but not a sequence of them.

    When is the GIL released?

    • Blocking I/O: files, sockets, time.sleep().
    • Many C extensions while they crunch numbers — NumPy, hashing (hashlib), compression (zlib), many database drivers. That's why NumPy-heavy code can use several cores even with threads.

    Other Pythons

    The GIL is a CPython feature. Jython and IronPython never had one; PyPy has its own. In everyday conversation, “Python” means CPython.

    ⚠️ Gotchas checklist

    Skim this the night before an interview.

    1. Python is compiled (to bytecode), not purely interpreted.
    2. .pyc is version-specific.
    3. Constant folding: 24 * 60 * 60 is computed at compile time.
    4. __del__ timing is unpredictable — use context managers.
    5. Refcounting is deterministic: refcount 0 → freed immediately.
    6. The cyclic GC only handles cycles — refcounting does most of the work.
    7. gc.disable() disables the cycle collector only.
    8. The GIL protects CPython internals, not your data structures.
    9. counter += 1 is not atomic — use a lock.
    10. I/O-bound → threads work. CPU-bound → multiprocessing.
    11. Free-threaded (no-GIL) Python is a separate build, not the default.
    12. pymalloc handles objects ≤ 512 bytes; bigger ones go to the OS allocator.
