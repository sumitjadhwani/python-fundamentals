    MODULE 11

    Compilation & Bytecode

    🔑 Core idea

    Python is compiled to bytecode, then that bytecode is interpreted by the Python Virtual Machine (PVM). So it's both — there is a compile step, but it produces bytecode (.pyc), not machine code.

    Source .py → Tokenizer → AST → Compiler → Bytecode .pyc → PVM executes
    🧠 Memory trick

    “Translate once, cook many times.”

    The compiler translates your recipe into kitchen shorthand (bytecode) and keeps it in __pycache__. The chef (PVM) cooks from the shorthand every run.

    Peek at the bytecode with dis

    import dis

def add(a, b):
    return a + b

dis.dis(add)
      RESUME                            0
  LOAD_FAST_BORROW_LOAD_FAST_BORROW 1 (a, b)    ← push a and b
  BINARY_OP                         0 (+)       ← pop two, push a + b
  RETURN_VALUE                                  ← pop and return

    Output from Python 3.14. Opcode names change between versions (older ones show LOAD_FAST / BINARY_ADD) — the shape is what matters.

    It's a stack machine

    🧠 Memory trick — a stack of plates

    LOAD_* puts a plate on the stack. BINARY_OP takes two plates off and puts the result back. STORE_* takes the top plate and gives it a name. RETURN_VALUE hands the top plate to the caller.

    .pyc files

    • Live in __pycache__/, named per version: module.cpython-314.pyc.
    • Rebuilt when the source changes (timestamp or hash check).
    • Version-specific — 3.12 bytecode won't run on 3.14.
    • PYTHONDONTWRITEBYTECODE=1 stops Python writing them.
    • The script you run directly isn't cached — only imported modules are.

    Constant folding

    def seconds_per_day():
    return 24 * 60 * 60

seconds_per_day.__code__.co_consts   # (24, 86400) — 86400 was computed at COMPILE time

# Folding has limits: "a" * 1000 is folded, a huge "a" * 10_000 is not
# (CPython won't bake very large constants into the .pyc)

    Code objects

    def example(x):
    return x * 2 + 1

code = example.__code__
code.co_varnames     # ('x',)         local names
code.co_consts       # constants used (exact tuple varies by version)
code.co_stacksize    # max stack depth the function needs

c = compile("1 + 2", "<string>", "eval")   # compile a string yourself
eval(c)              # 3
    ⚠️ Don't forget
    • “Interpreted vs compiled?” → both: compiled to bytecode, then interpreted.
    • Bytecode isn't portable across Python versions.
    • Since 3.11 the interpreter specializes hot bytecode (adaptive interpreter) — one reason modern Python got faster.
    🤔 Predict the output
    def f():
    return 60 * 60

print(3600 in f.__code__.co_consts)
    Show answer 
    True

    The compiler folded 60 * 60 into 3600, so the multiplication never happens at runtime.

    MODULE 12

    Memory Management: How Python Cleans Up

    💬 In plain English

    In Python you never free memory yourself. Python keeps a count of how many things are using each object. The moment nothing uses an object any more, Python throws it away. A backup cleaner, the garbage collector, handles one tricky case: objects that only point at each other.

    🎈
    Balloons on strings.

    Every object is a balloon. Every variable, list slot or dict entry that refers to it is a string someone is holding. While at least one string is held, the balloon stays. When the last string is let go, the balloon floats away — the memory is freed.

    1. Reference counting: the main cleaner

    The number of strings on a balloon is its reference count. To see the moment an object is freed, this demo uses __del__, a method Python calls just before throwing an object away:

    class Balloon:
    def __init__(self, name):
        self.name = name
    def __del__(self):                 # demo only: shows the moment it's freed
        print(f"{self.name} popped")

a = Balloon("red")     # 1 string  (a)
b = a                  # 2 strings (a, b)
del a                  # 1 string left — nothing happens
print("still here")    # → still here
del b                  # 0 strings → → red popped
    🧠 Memory trick

    “del lets go of a string — it doesn't pop the balloon.”

    The object is freed only when the last reference is gone.

    What counts as a string?

    Not just variables. Anything that holds on to an object keeps it alive:

    blue = Balloon("blue")
party = [blue]           # the list holds a string too
del blue
print("list still holds it")   # → list still holds it
party.clear()                  # → blue popped

def make():
    tmp = Balloon("green")     # a local variable is a string…
    print("inside")
make()                         # → inside
                               # → green popped   …let go when the function returns

    That's why most memory in Python cleans itself up without you thinking about it: local variables vanish when functions return, and temporary objects vanish as soon as you're done with them.

    2. The one problem: objects holding each other

    🪢
    Two balloons tied to each other.

    Nobody is holding either balloon — but each one is tied to the other, so each still has one string. Counting strings alone, they'd stay forever. This is called a reference cycle.

    import gc

x = Balloon("A")
y = Balloon("B")
x.friend = y           # A holds B
y.friend = x           # B holds A   ← a cycle
del x, y               # we let go — but nothing pops!
print("nothing popped yet")   # → nothing popped yet

gc.collect()           # → A popped
                       # → B popped   the garbage collector found the cycle

    3. The garbage collector: the backup cleaner

    The garbage collector (gc) wakes up every so often, looks for groups of objects that only point at each other and that nothing else can reach, and frees them. It runs automatically — you almost never call gc.collect() yourself.

    🧠 Memory trick — bouncer and cleaning crew

    Reference counting is the bouncer: the instant the last guest stops holding an object, it's out — immediately. The garbage collector is the cleaning crew that sweeps through now and then to clear the tangled leftovers the bouncer can't see.

    To keep the sweeps cheap, it uses a simple observation: most objects die young. So it checks new objects often and long-lived survivors rarely. These age groups are called generations.

    4. Weak references: looking without holding

    Sometimes you want to keep track of an object without keeping it alive — for example, a cache. A weak reference points at a balloon without holding its string.

    import weakref

big = Balloon("gold")
ref = weakref.ref(big)   # look, but don't hold
print(ref().name)        # → gold
del big                  # → gold popped   the weak ref didn't keep it alive
print(ref())             # → None
    ⚠️ Common mistake 1: using __del__ for cleanup

    __del__ is fine for a demo, but in real code you can't be sure when it runs (cycles delay it, and it may not run at all when the program exits). For files, connections and locks, use with (Phase 2, Module 9) — cleanup then happens at a known moment.

    ⚠️ Common mistake 2: “leaks” from things you forgot you're holding

    Python can't free an object while something still references it. The classic leak is a cache that only ever grows:

    _cache = {}

def load_user(user_id):
    if user_id not in _cache:
        _cache[user_id] = fetch_from_db(user_id)   # ❌ every user stays in memory forever
    return _cache[user_id]

from functools import lru_cache

@lru_cache(maxsize=1000)                           # ✅ keeps only the 1000 most recently used
def load_user(user_id):
    return fetch_from_db(user_id)
    🤔 Predict the output
    nums = [1, 2, 3]
backup = nums
del nums
print(backup)
    Show answer 
    [1, 2, 3]

    del nums only removed one name. backup is still holding the list, so it stays alive.

    ✅ Remember
    • Python counts references; when the count hits zero, the object is freed immediately.
    • Objects that only point at each other (cycles) are cleaned up later by the garbage collector.
    • del removes a name, not the object.
    • Use with for cleanup, and watch out for caches and lists that grow forever.
    🔬 Go deeper — getrefcount, generations, allocators, leak hunting

    Seeing the count

    import sys
x = [1, 2, 3]
sys.getrefcount(x)   # → 2   x, plus a temporary reference for the call itself

    The count always reads one higher than you'd expect, because passing x into getrefcount creates a reference.

    Generations in numbers

    Python versionLayoutgc.get_threshold()
    ≤ 3.13 (classic)3 generations: gen 0 (new) → gen 1 → gen 2 (long-lived)(700, 10, 10)
    3.14+Incremental: a young and an old generation, scanned in small steps so pauses are shorter(2000, 10, 0)

    Classic rule: gen 0 is checked when allocations minus deallocations exceed 700; gen 1 every 10 gen-0 runs; gen 2 every 10 gen-1 runs. Interview answers usually quote this model.

    gc.disable()

    Turns off only the cycle collector — reference counting keeps working. Some apps disable it during hot paths and call gc.collect() at quiet moments.

    How memory is actually handed out

    ┌───────────────────────────────────────────────┐
│ Layer 3: object-specific caches (ints, lists…)│
├───────────────────────────────────────────────┤
│ Layer 2: pymalloc — objects ≤ 512 bytes        │
│   Arena (256 KB) → Pool (4 KB) → Block (8–512 B)│
├───────────────────────────────────────────────┤
│ Layer 1: the OS malloc — anything bigger        │
└───────────────────────────────────────────────┘

    Freed small objects go back to Python's own pools for reuse, so a process's memory use may not shrink right away even after objects die.

    Finding leaks with tracemalloc

    import tracemalloc

tracemalloc.start()
run_suspicious_code()
snapshot = tracemalloc.take_snapshot()
for stat in snapshot.statistics("lineno")[:5]:
    print(stat)          # the 5 source lines that allocated the most memory

    More on weak references

    weakref.WeakValueDictionary is a dict whose entries disappear automatically when their values are freed — a cache that never keeps objects alive by itself.

    MODULE 13

    The GIL (Global Interpreter Lock)

    🔑 Core idea

    The GIL is a mutex that lets only one thread run Python bytecode at a time. It exists because CPython's reference counts aren't thread-safe. It blocks CPU parallelism with threads — but I/O-bound threads work fine, because the GIL is released while waiting on I/O.

    🧠 Memory trick — the one-microphone room

    Only the person holding the mic (thread) can speak (run bytecode). When someone steps out for food (I/O), the mic is free for others. Shouting louder (more threads) doesn't make two people speak at once.

    Thread 1:  ████░░░░████░░░░████
Thread 2:  ░░░░████░░░░████░░░░
               ↑ the interpreter asks for a switch every 5 ms (sys.getswitchinterval())

    What the GIL does — and doesn't — protect

    ✅ Protects

    • CPython internals (refcounts, allocator)
    • Each single bytecode instruction

    ❌ Does NOT protect

    • Your data structures
    • Multi-step operations like counter += 1
    • The logic of your program
    🧠 Memory trick

    “The GIL guards Python's guts, not your data.”

    Why counter += 1 isn't thread-safe

    LOAD_GLOBAL     counter   ← read
LOAD_SMALL_INT  1
BINARY_OP       (+=)      ← add
STORE_GLOBAL    counter   ← write      (a thread switch can land between any two)
    import threading

counter = 0
lock = threading.Lock()

def increment():
    global counter
    for _ in range(1_000_000):
        with lock:            # without the lock, updates can be lost
            counter += 1

threads = [threading.Thread(target=increment) for _ in range(2)]
for t in threads: t.start()
for t in threads: t.join()
print(counter)                # 2000000 — guaranteed only because of the lock

    When is the GIL released?

    • Blocking I/O — files, sockets, time.sleep()
    • Many C extensions while crunching numbers (NumPy, hashing, compression, DB drivers)

    The decision rule

    BottleneckUseWhy
    I/O-boundThreads (or asyncio)GIL is released while waiting
    CPU-boundMultiprocessingEach process has its own GIL
    Bothasyncio + ProcessPoolExecutorAsync for I/O, processes for compute

    The free-threaded future (PEP 703)

    Python 3.13 shipped an experimental free-threaded build with no GIL (python3.13t). In 3.14 that build is officially supported, but it's still a separate build — the regular python keeps the GIL. Check with sys._is_gil_enabled().

    ⚠️ Don't forget
    • The GIL makes CPython safe, not your code — always lock shared mutable state.
    • Threads don't speed up pure-Python CPU work; they can even slow it down.
    🤔 Predict the output
    # Same counter program as above, but WITHOUT the lock.
# What does print(counter) show?
    Show answer 
    Unpredictable — anything up to 2000000.

    On some versions and machines it often prints the right number, which makes the bug worse: the code is still wrong and can lose updates at any time. Correctness must come from the lock, not from luck.

    ⚠️ Gotchas checklist

    Skim this the night before an interview.

    1. Python is compiled (to bytecode), not purely interpreted.
    2. .pyc is version-specific.
    3. Constant folding: 24 * 60 * 60 is computed at compile time.
    4. __del__ timing is unpredictable — use context managers.
    5. Refcounting is deterministic: refcount 0 → freed immediately.
    6. The cyclic GC only handles cycles — refcounting does most of the work.
    7. gc.disable() disables the cycle collector only.
    8. The GIL protects CPython internals, not your data structures.
    9. counter += 1 is not atomic — use a lock.
    10. I/O-bound → threads work. CPU-bound → multiprocessing.
    11. Free-threaded (no-GIL) Python is a separate build, not the default.
    12. pymalloc handles objects ≤ 512 bytes; bigger ones go to the OS allocator.
